## 3. Findings

### DB-01 — `unlockSubmission()` on an interactive taker poisons the Grade tab's batch save for the whole section
**Severity:** High · **Category:** integrity
**Location:** `site/js/faculty-grade.js:847-854`, `:196-200` (`isEffortGraded`), `:281-322` (`gradeRows`); constraint `supabase/migrations/app/014_effort_grades_per_row.sql:107-109`

**What:** `unlockSubmission()` sets `chosen_activity_id: null, status: 'draft'` and **never touches `grades`**.
An interactive taker already has `effort` non-NULL, `question_scores='{}'`, `source='derived'`,
`is_finalized=true` from the 015 trigger. Post-unlock, `isEffortGraded()` returns false — it keys solely on
`submission.chosenActivityId`. So `buildGradeData()` (line 221) stops excluding them and `gradeRows()` rule 2
doesn't skip them (a prior grade exists, line 290). The emitted row carries non-empty `question_scores`
(all questions default `status:'zero'`, no written answers). The DB row still holds `effort`, violating
`CHECK (effort IS NULL OR question_scores = '{}'::jsonb)`.

**Why it matters:** PostgREST sends the batch as one statement in one transaction — the violation rejects
**every row**, not just the offender. The instructor sees Save draft and Finalize & publish fail for the whole
section with an opaque `23514` and no indication which student caused it. The comment at
`faculty-grade.js:213-215` calls this CHECK "the second line of defence"; the unlock path hits it as the
*first*, where nothing else guards.

**Confidence:** Confirmed (all three code paths + constraint in repo; whether such a row exists live is §4 query 8)
**Fix:** Either (a) make `isEffortGraded()` fall back to `grade.effort != null` — the more honest predicate,
since that is what the constraint keys on — or (b) have `unlockSubmission()` clear the derived grade in the
same operation. (a) is safer mid-term: no stored data changes.
**Requires DDL?** No.
**Live risk:** High. Unlocking is routine ("cadet picked the wrong path") and this blocks grading for a section at publish time.

### DB-02 — `displayPoints()` shows a written taker **0 points** on any `grading_mode='effort'` offering
**Severity:** High · **Category:** drift
**Location:** `site/js/schema.js:697-711`; consumers `student-data.js:134`, `student-lessons.js:147`, `site/student/assignments.html:195`

**What:** Migration 014 re-keyed grading off the **grade row** (`effort IS NULL` → trigger leaves
`points_earned` alone). Display did not follow:
```js
export function pointsFromEffort(effort, pointsPossible) {
  if (effort == null) return 0;          // ← trigger says "leave alone"; this says "zero"
  ...
}
export function displayPoints(grade, offering) {
  if (offering?.gradingMode === 'effort') {   // ← still keys off the OFFERING
    return pointsFromEffort(grade.effort, ...);
  }
  return grade.points_earned == null ? null : Number(grade.points_earned);
}
```
A written taker on such an offering has `effort = NULL` (correct per `WRITTEN-SCHEMA1.md`, mandatory per the
CHECK) and real points in `points_earned`. `displayPoints` returns `0`. Migration 014's header calls
`grading_mode` "advisory for display" — it is not; it selects the number shown.

**Why it matters:** Exactly the silent-zero bug 014 closed server-side, still live client-side, and all three
consumers are **student-facing**. Latent today only because `faculty-lessons.js:715` writes
`grading_mode: model.gradingMode || 'points'` — but the **DB default is `'effort'`** (`app/001:256`), so any
script or hand INSERT omitting the column lands on the broken path.

**Confidence:** Likely (defect Confirmed; live existence of an effort offering is §4 query 3)
**Fix:** Discriminate on `grade.effort != null`, mirroring the trigger; return `points_earned` otherwise.
**Requires DDL?** No. (Changing the column default *would* — fold into a future unseal, not worth one alone.)
**Live risk:** High if any effort offering exists — a student seeing 0 on completed work.

### DB-03 — DDL on `app` is **not** sealed; `prep_app_owner` has been `LOGIN` since 2026-07-23
**Severity:** High · **Category:** migration-hygiene
**Location:** `.ai/instructions/CORE.md` §0; `CHANGELOG.md:794-795, 2187-2188, 2271-2275, 2704-2705, 2722-2727, 3335-3336, 5047, 5213-5215, 5305-5309`; `docs/ROADMAP.md:101-113` (P0.2, open)

**What:** CORE.md §0 asserts the owner was set `NOLOGIN` and "cannot connect at all". It was unsealed for
014/015 on 2026-07-23 and flagged as still unsealed **at least nine times since**, most recently for 019 on
2026-07-30. No entry records a re-seal. P0.2 remains open.

**Why it matters:** (1) The property CORE.md promises does not hold — the coordination gate treats sealing as
the structural reason concurrent DDL cannot happen. (2) It corrupts downstream reasoning: CORE.md §2 justifies
hardcoding the deadline hour in three places *because* DDL is sealed, and several decisions defer fixes to
"the next unseal" that is already open. `CHANGELOG.md:2722-2726` records migration 016's header being stale in
precisely this way.

**Confidence:** Likely — repo record is unambiguous it was left open and never recorded closed; only `pg_roles` proves today (§4 query 1).
**Fix:** Human-only, as `postgres`: `ALTER ROLE prep_app_owner NOLOGIN;` (no agent role holds `CREATEROLE`).
**Then correct CORE.md §0 either way** — if it stays unsealed deliberately, CORE.md must say so.
**Requires DDL?** No — role change, and the role is reachable.
**Live risk:** Low direct, high indirect — it is the assumption the no-concurrent-DDL discipline rests on.

### DB-04 — Students can rewrite or delete their own submitted work after commit
**Severity:** High · **Category:** integrity
**Location:** `supabase/migrations/app/002_rls.sql:331-343`; no guard trigger exists — every `CREATE TRIGGER` in the chain enumerated, only `submission_activities_touch` (updated_at)

**What:** `CREATE POLICY sa_student_write ON submission_activities FOR ALL TO authenticated` with predicates
naming only enrolment ownership. `FOR ALL` includes UPDATE **and DELETE**; neither predicate mentions
`submissions.status`, `is_final`, or an existing finalized grade. `PROJECT.md`'s "the receiver page and the
data layer refuse a second report once a finalized grade exists" is entirely **application-level**. By
contrast `submissions` is correctly protected — SELECT/INSERT/UPDATE for students, **no DELETE policy at all**.
The container is locked; the contents are not.

**Why it matters:** `INTERACTION-DATA-CONTRACT` §7 designates `report_markdown` as the audit trail justifying
auto-finalizing an interactive grade without review. A student can DELETE that row or PATCH its
`content`/`report_markdown` via direct REST post-finalization. The grade survives (015 fires on `submissions`),
so the score isn't directly manipulable — but the evidence is, defeating the "an instructor can reopen one if
a report looks tampered" escape hatch in 015's header. For written takers, deletion also removes the answers
an instructor would regrade against.

**Confidence:** Confirmed
**Fix:** Narrow to `FOR INSERT`/`FOR UPDATE` (drop student DELETE) plus `AND s.status <> 'committed'`; or a
`BEFORE UPDATE OR DELETE` trigger refusing when the parent is committed and a finalized grade exists. Trigger
form preferred for migration 006's stated reason: `WITH CHECK` cannot see `OLD`.
**Requires DDL?** **Yes** — but see DB-03; the owner is very likely already `LOGIN`. Batch with DB-07, DB-08, DB-13 so one window covers all four.
**Live risk:** Medium — requires deliberate REST calls, but the population is cadets with an incentive and the endpoint is public.

### DB-05 — `public` and `app` share five table names, and a dropped profile header silently targets the wrong one
**Severity:** Medium · **Category:** legacy
**Location:** `supabase/schema.sql` + `supabase/migrations/*.sql` vs `app/001_core_model.sql`; `site/js/config.js:21-22`; `.ai/skills/preflight-analyze/SKILL.md:89-105, 811, 832`

**What:** `public` still holds `assignments`, `students`, `sections`, `instructors`, `extensions` — five central
names also in `app`. `config.js:21` notes `app` had to be *added* to Exposed schemas, meaning `public` was
already there and, as PostgREST's default, is what any request **without** `Accept-Profile`/`Content-Profile`
resolves to. The preflight-analyze runbook knows this ("every request names its schema", SKILL.md:832) with a
troubleshooting note at :811 — a documented tripwire, not a barrier. For a *write*, the failure is not a 404
but a **successful write to the wrong table**.

**Why it matters:** This is the concrete cost of retaining `public`. All `scripts/` tooling hand-rolls REST
calls via `urllib`; one forgotten `Content-Profile: app` writes into `public.students` with no error — and is
simultaneously a silent *non*-write to the live table.

**Confidence:** Likely — collisions and default-schema behaviour Confirmed; current Exposed-schemas list is §4 query 6.
**Fix:** Do **not** drop `public` (authorized rollback, `PREP-V2-SCHEMA.md` §8). Make it unmistakably inert:
1. **Remove `public` from Exposed schemas** — dashboard setting, not DDL, no unseal, reversible in one click,
   converting silent-wrong-write into a loud 404. **Highest value-per-effort change in this report.**
2. `REVOKE ALL ON ALL TABLES IN SCHEMA public FROM anon, authenticated;`
3. `COMMENT ON SCHEMA public IS 'RETIRED 2026-07-28 — cutover rollback only. Do not read or write. See docs/decisions/PREP-V2-SCHEMA.md §8.';`

**Requires DDL on `app`?** No — none touch `app`; (2)/(3) are DDL on `public`, unsealed.
**Live risk:** Low to apply; removes unbounded risk. Reversibility keeps it compatible with the rollback role.

### DB-07 — `staff_assignments.role` still admits `grader`, retired 2026-07-27
**Severity:** Medium · **Category:** integrity
**Location:** `supabase/migrations/app/001_core_model.sql:240`; **confirmed live** via `db-schema.js` → `staff_assignments.enums.role == ["director","instructor","grader"]`

**What:** CHECK is `role IN ('director','instructor','grader')`. `grader` was retired as privilege-identical to
`instructor`, `create-instructor` refuses it, no UI offers it — but the DB still accepts it. Because
`db-schema.js` is live-introspected, this is confirmed present in the live database, not just the file.

**Why it matters:** A direct DML write can still create a `grader` row, and `site/faculty/system.html`'s generic
table browser renders enums from `db-schema.js` — so it **offers `grader` in a dropdown**. Authorization keys
on `director` vs. everything-else, so a `grader` behaves as an instructor; the risk is drift, not escalation.

**Confidence:** Confirmed
**Fix:** `ALTER TABLE app.staff_assignments DROP CONSTRAINT staff_assignments_role_check, ADD CONSTRAINT staff_assignments_role_check CHECK (role IN ('director','instructor'));` — preceded by §4 query 4, since existing `grader` rows must be migrated first or the ALTER fails.
**Requires DDL?** **Yes** — one short window, fast statement, tiny table. Batch with DB-04/08/13.
**Live risk:** Very low.

### DB-08 — Deleting a student hard-cascades to submissions and grades, with no soft-delete guard
**Severity:** Medium · **Category:** integrity
**Location:** `app/001_core_model.sql:210, 335-336, 389`; policy `app/002_rls.sql:239` (`students_write ... FOR ALL`)

**What:** `students → enrollments → submissions → submission_activities` and
`students → enrollments → grades → grade_events` are `ON DELETE CASCADE` at every hop. `students_write` is
`FOR ALL` (includes DELETE) and admits any director of an offering the student is enrolled in. One
`DELETE FROM students` destroys that cadet's work, grades, and the append-only `grade_events` audit that exists
because "a retroactive rescore silently corrupted totals in the old system once already".

**Why it matters:** The model already has the correct soft path — `enrollments.status IN ('active','dropped','completed')` —
and `PREP-V2-SCHEMA.md` §1 names silent re-attribution of history as a fault v2 was built to fix. Nothing
routes a director toward `dropped`, and nothing makes the destructive option harder than the safe one.

**Confidence:** Confirmed (schema + policy explicit); whether the UI exposes a delete button is a frontend question — the REST surface exposes it regardless.
**Fix:** No-DDL version: confirm the roster UI offers only "drop", and document the cascade in `director-course-structure.md`. DDL version: `BEFORE DELETE ON students` trigger refusing when any `grades` row exists.
**Requires DDL?** Only for the trigger form. **Live risk:** Low probability, catastrophic and unrecoverable impact.

### DB-10 — The Grade panel is the only hot path that does not chunk its `.in()` lists
**Severity:** Low · **Category:** performance
**Location:** `site/js/faculty-grade.js:110-116, 522, 623-627, 826-830`; helper `site/js/schema.js:933-939`

**What:** `schema.js` defines `export const CHUNK = 300` — *"Chunk an id list so `.in()` URLs stay under GET
length limits on large courses."* `faculty-rollup.js` uses it four times, `faculty-gradebook.js` and
`faculty-data.js` three more. **`faculty-grade.js` imports it nowhere** and passes full `enrollmentIds` into
`.in()` at four sites, including cross-offering queue loaders (623-627, 826-830) that additionally multiply by `offeringIds`.

**Why it matters:** ~37 bytes per uuid; 700 enrolments on "All sections" is a ~26 KB query string on a GET —
past the practical ceiling for several proxies. Failure is a 414 **or a truncated filter**, and truncation is
the dangerous mode: it returns a silent *subset*, so the panel shows fewer students than the section holds
rather than erroring. Physics 215's sections are likely small enough; Physics 110 at full enrolment is the scale that trips it.

**Confidence:** Likely (asymmetry Confirmed; live scale is §4 query 5)
**Fix:** Import `chunked` and wrap the four `.in('enrollment_id', …)` sites as `faculty-gradebook.js:462-468` already does.
**Requires DDL?** No. **Live risk:** Low today, scaling with roster.

### DB-14 — JSONB payloads have specs but no write-time validation in the database
**Severity:** Low · **Category:** jsonb-contract
**Location:** `grades.question_scores`, `grades.diagnostic` (`app/001:396-397`), `submission_activities.content` (`:369`), `analysis_reports.payload` (`:450`)

**What:** All four are `jsonb NOT NULL DEFAULT '{}'` with no shape CHECK. The only DB constraints are size caps
(`content ≤ 32768 bytes`, `report_markdown ≤ 100000 chars`) and the cross-column `grades_one_grading_mechanism`.
Validation lives in producers: `lesson_aggregate.py:1413-1440` validates scope keys, prose lengths, and that
`section_notes` appear only on an `instr:` scope; the preflight-analyze skill validates against
`WRITTEN-SCHEMA1.md`; the 015 trigger validates `content->'effort'` narrowly and correctly.

**Why it matters:** This is **defensible** given sealed DDL and evolving shapes — CHECK constraints are not
recommended. The finding is that consumer-side defensive reads are the only surviving record of past drift, and
they map it: `schema.js:866-876` (`effortSignal`) resolves effort through **four** fallbacks in precedence —
`grades.effort`, the written report on the grade, `writtenSignals`' diagnostic pair, then a student-`claimed`
value from the report payload. Four sources for one number is a fossil record.

**Confidence:** Confirmed
**Fix:** No DDL, no code change. One page in `docs/contracts/` enumerating, per column, its spec location,
producers, and consumers — currently spread across `WRITTEN-SCHEMA1.md`, `INTERACTION-DATA-CONTRACT.md`,
`ROLLUP-AGREEMENT.md`, `INTERACTION-AGGREGATION.md`, and inline comments. Register in `docs/DOC-SOURCES.json`.
**Live risk:** None.

## 5. Positive findings

- **`site/js/db-schema.js` is the best artifact in the data layer.** Live-introspected, committed, regenerated
  by a read-only script connecting as the SELECT-only tier (explicitly documented as *not* a coordination
  event), drift-checked by `tests/app-schema/test-db-schema.mjs --check`. It let this audit confirm live state
  without connecting. **Diffing it against the `app` chain found zero discrepancies.**
- **The `app` RLS model delivers what `PREP-V2-SCHEMA.md` promised.** 62 bespoke `public` policies replaced by
  a two-predicate core over SETOF helpers (`my_enrollments()`, `staff_sections()`, `director_offerings()`).
  All four named July 2026 audit findings are visibly closed in `002_rls.sql` — roster no longer world-readable,
  grades require owner check *and* finalization (`grades_own_finalized`, whose comment names the exact `public`
  defect), students cannot delete each other, no student can write another's work.
- **Migration headers are genuinely load-bearing documentation.** 014, 015, 019 each open with
  why-this-exists, the bug closed, what changes for existing data *with counts verified against live before
  writing*, and a read-only VERIFY block. 019 proves a zero-row change ("213 grade rows, 78 carry effort, every
  one on a 2.00 offering") rather than asserting it. Those VERIFY blocks were reused in §4.
- **The 015 autograde trigger is carefully written.** `SECURITY DEFINER` with pinned `search_path`, scoped to
  the firing submission's own enrolment+offering, the §5.2 reflection cap re-applied server-side because effort
  rides in a student-controlled hash, and `ON CONFLICT … WHERE is_finalized = false OR source = 'derived'`
  letting a re-submit replace a derived grade but never a human's. Its `IS DISTINCT FROM` comment (lines 97-100)
  correctly identifies that `jsonb_typeof(...) <> 'number'` evaluates NULL and falls *through* the guard for an
  absent `effort` — a subtle three-valued-logic bug caught before shipping.
- **Migration 006 is a model of its kind.** Two real bypasses (self-attributed unlock; status-revert-then-switch),
  each *reproduced against live as a signed-in student* rather than reasoned about, fixed in the trigger with an
  explicit argument for why not RLS (`WITH CHECK` cannot see `OLD`), plus a deliberate documented exception for
  `uid IS NULL` operator connections.
- **Effort-curve copies agree.** Five of the six named in 019's header are logically identical —
  `app.grades_points_from_effort()`, `pointsFromEffort()` (`schema.js:697`), `pointsForEffort()`
  (`faculty-rollup.js:582`), `points_from_effort()` (`interaction_reports.py:103`), `_points_for_effort()`
  (`lesson_aggregate.py:213`) — all using `min(1, points_possible)` on the 1-2 branch; `grade_interactive.py`
  imports rather than copying, as claimed. The **only** divergence is the NULL-effort case (DB-02), a different
  question from the curve itself.
- **Indexing is thorough on the paths that matter.** `enrollments` indexed both ways with a partial index on
  `section_id WHERE status='active'` matching the actual predicate; `grades`/`submissions` get enrolment lookups
  free from `UNIQUE (enrollment_id, assignment_offering_id)` (enrolment leading, so usable);
  `grades_unfinalized_idx` partial on `WHERE NOT is_finalized`, matching the grading-queue predicate exactly;
  `extensions` indexed on both FKs. **No missing index found on a hot path.**
- **`chunked(list, 300)` exists and is used in rollup, gradebook, and the shared faculty data layer** — the
  URL-length problem was already found and solved. DB-10 is a coverage gap in one module, not an unrecognized issue.
- **All six edge functions pin `{ db: { schema: "app" } }`** on both admin and caller-scoped clients;
  `provision-students/index.ts:14` even carries "`public` is no longer touched by this function."
- **`analysis_runs` has a SELECT-only policy** — the browser reads run history for the task banner but cannot
  forge a run record. Correct split.
- **Retired-field discipline is real.** `misconception_trends` retirement is recorded in four places including a
  struck-through SKILL.md heading, and `lesson_aggregate.py:1058-1066` explains precisely why the read path must
  still tolerate it. DB-11 is a one-line residue on an otherwise well-executed deprecation.

## 6. Onboarding blockers

1. **There is no way to answer "how is this database built?" from the repo.** No ledger, no
   `supabase/migrations/README.md`, two independently numbered chains, a missing `002`, seven unordered loose
   files, one deliberately-unapplied migration that looks pending, and a bootstrap script outside both chains
   creating the roles and deferring two FKs to a `postgres`-only snippet. The answer exists only as prose across
   5,300 CHANGELOG lines. **Highest-value documentation fix in the repo**, and cheap.
2. **CORE.md §0 says DDL on `app` is sealed, and it very likely is not** (DB-03). New agents plan around that
   sentence. Nine CHANGELOG entries flag the gap; none corrects the file agents actually read.
3. **`public` and `app` share five central table names with a silent default-schema fallback** (DB-05). A
   newcomer's first REST script has a coin-flip chance of a header they don't know they need, and the failure is
   a successful write to the wrong table. One dashboard click makes it a loud 404, fully reversibly.
4. **`site/js/faculty-report.js` looks like the Report page's data layer and is not** (DB-06). Excellent header,
   defeated by its location.
5. **Reproducing the data layer locally needs credentials that cannot come from the repo** —
   `supabase/admin/.env` (three `prep_app_*` roles), `supabase/admin/config.json` (`claude_code_recker`,
   `public`-era tooling), and `~/.claude/skills/preflight-analyze/config.json`. CORE.md §3 documents this and
   notes the decided-but-unexecuted move to `$PREP_CONFIG`; the Claude-branded path is real friction for a Codex operator.
6. **`db-schema.js` is the closest thing to a schema source of truth and nothing top-level says so.** Mentioned
   only in its own header and in `gen_db_schema.py`. It deserves a line in PROJECT.md's Key Files table.
7. **Four JSONB contracts are specified across five documents plus inline comments** (DB-14). Touching
   `grades.diagnostic` requires finding `WRITTEN-SCHEMA1.md`, `INTERACTION-DATA-CONTRACT.md`,
   `ROLLUP-AGREEMENT.md`, `INTERACTION-AGGREGATION.md`, and `schema.js:866`. One index page collapses that.
