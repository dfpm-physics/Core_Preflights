# PREP — Security & Authorization Audit
*Static source analysis only — no network, no DB, no scripts run, no repo files modified.*
*Excluded (in-flight artifact library) per instruction.*

**Counts:** 2 Critical · 4 High · 5 Medium · 6 Low

## Framing fact that colours everything

`supabase/admin/app_schema_bootstrap.sql:118-129` grants `SELECT, INSERT, UPDATE, DELETE` on **all
tables** in `app` to `anon`, `authenticated`, `service_role`, with matching `ALTER DEFAULT PRIVILEGES`.
There are **no column-level grants anywhere** and no `FORCE ROW LEVEL SECURITY`. So **RLS is the only
gate**, it works at *row* granularity only, and any table whose policy admits a row admits **every
column of that row**, read and write. SEC-01, SEC-03 and SEC-09 follow directly from that.

### SEC-01 — Any instructor can promote themselves to system admin with one API call
**Severity:** Critical
**Location:** `supabase/migrations/app/002_rls.sql:263-264`; enabled by `supabase/admin/app_schema_bootstrap.sql:118-129`

**What:** `CREATE POLICY instructors_update_own ON instructors FOR UPDATE TO authenticated USING (id = current_uid()) WITH CHECK (id = current_uid());`
restricts *which row*, never *which columns*. `app.instructors` carries `is_global_admin`, which
`app.is_admin()` (`002_rls.sql:67-71`) reads, and which short-circuits `staff_offerings()`,
`director_offerings()`, `director_courses()`, `staff_sections()`, `students_write`,
`instructors_admin_write`, `courses_write`, `terms_write`, `kinds_write`, `feedback_admin_read`.
Every `app` migration was read: there is **no trigger on `instructors` at all**. `authenticated`
holds UPDATE on the whole table.

**Exploit:** Any staff member — an instructor assigned to one section — opens devtools on any PREP
page (the shared client is `window.db`):
```js
await db.from('instructors').update({ is_global_admin: true })
        .eq('id', (await db.auth.getUser()).data.user.id)
```
They are now system admin across both courses and every term: every roster row (name, email,
squadron, sex, majors, advisor), every submission, every grade, every EI note, all in-app feedback,
plus `site/faculty/system.html` — a generic CRUD browser over every table in `app`. They can delete
students (cascading submissions and grades), mint system admins via `create-instructor`, and remove
real ones via `remove-instructor`. **Nothing is recorded** in `grade_events` or `analysis_runs`,
because the promotion is a plain UPDATE. This also defeats every server-side check in all six edge
functions, since they all gate on exactly this flag from exactly this table.

**Confidence:** Confirmed — policy, absence of column grant, absence of trigger, and the downstream
`is_admin()` consumers all traced. `supabase/admin/app_rls_test.py` has no test for this transition.

**Fix:** Preferred: `REVOKE UPDATE (is_global_admin) ON app.instructors FROM authenticated, anon;` —
one statement, leaves `instructors_admin_write` and the service-role functions working. Alternatively
a `BEFORE UPDATE` trigger rejecting a change to the flag unless `current_uid() IS NULL` or the caller
was already admin (same shape as `review_signoffs_require_self()` in `007`). Also narrow the policy
itself — `account.js` never writes this table, so it may be droppable outright.

**Live-system risk of fixing:** The `REVOKE` is **not DDL on schema objects — no `prep_app_owner`
unseal needed**, runnable as `postgres`. Ships in seconds, invisible to students. The trigger variant
*is* DDL and needs the §0 unseal.

### SEC-02 — A student can write their own grade on any interactive assignment
**Severity:** Critical
**Location:** `002_rls.sql:339-343` (`sa_student_write`) + `015_interactive_autograde.sql:92-141`

**What:** The autograde trigger is `SECURITY DEFINER`, owned by the `BYPASSRLS` app owner, and derives
a **finalized, student-visible** grade from a value the student's own browser wrote:
```sql
SELECT sa.content INTO v_content FROM submission_activities sa
 WHERE sa.submission_id = NEW.id AND sa.activity_id = NEW.chosen_activity_id;
v_effort := (v_content->>'effort')::int;
INSERT INTO grades (... effort ... source, is_finalized) VALUES (... 'derived', true)
```
`sa_student_write` is `FOR ALL` with only "this row hangs off my enrolment" — no `is_final`, no
`status`, no deadline. The trigger's header notes the effort "rides in a URL hash the student
controls" and re-applies the §5.2 reading-reflection **cap** server-side — but never re-derives the
**effort**, which is the value that becomes the score.

Two aggravators: the `ON CONFLICT ... WHERE grades.is_finalized = false OR grades.source = 'derived'`
clause makes a prior derived grade **replaceable**, and the trigger is `AFTER UPDATE OF status`, so
naming `status` in a SET list re-fires it. And `site/js/student-data.js:410-417` documents the
opposite belief in detail ("effort … becomes a grade only when staff or the analysis workflow reads
it") — true when written, silently invalidated by migration 015.

**Exploit:** No artifact needed:
```js
await db.from('submission_activities')
  .update({ content: { effort: 5, reading_reflection: { meaningful: true } } }).eq('id', saId)
await db.from('submissions')
  .update({ status: 'committed', chosen_activity_id: interactiveActivityId }).eq('id', submissionId)
```
Yields `source='derived'`, `is_finalized=true`, `points_earned = points_possible`. Auto-final, so **no
review queue catches it** (015, rule 2). Repeatable across every interactive preflight. The
hand-crafted `#d=` hash on the real receiver is the lower-skill version.

**Confidence:** Confirmed — policy, trigger, and `ON CONFLICT` predicate read end to end.

**Fix:** In the trigger: refuse to grade when `sa.updated_at > submissions.committed_at`; refuse to
re-grade an existing `derived` grade unless `is_staff() OR current_uid() IS NULL`; refuse past the
effective deadline. Structurally better: a `BEFORE UPDATE/DELETE` trigger on `submission_activities`
refusing any change once the parent submission is `committed` (the `006` instructor unlock already
exists to reopen). **That one guard closes SEC-02 and SEC-04 together.**

**Live-system risk:** DDL on `app` — needs the §0 unseal. Does **not** break students mid-term,
because the UI already treats a committed interactive submission as final
(`interaction-submit.html:181-187`); existing grades untouched. Not a 2-minute window — plan a proper
unseal and re-run the RLS suite.

### SEC-03 — The model answer for the graded question is shipped to every enrolled student
**Severity:** High
**Location:** `002_rls.sql:194-198` (`activities_student_read`) + `site/js/schema.js:24-30` + `site/js/student-data.js:73-77`

**What:** `activities.content` is one jsonb column holding the whole question set, and
`scripts/fall2026/build_fall_preflights.py:225-226` / `build_110_preflights.py:224-225` write
`q3["expected_response"]` — the graded JiTT question, 1 of 2 points. `activities_student_read` grants
SELECT on the **whole row**; RLS cannot redact a column. The client doesn't merely allow it —
`OFFERING_SELECT` embeds `activities(id,slug,modality,title,content)` and `loadAssignmentStatuses()`
runs it on the student dashboard, the assignments page, and the artifact receiver.

**Exploit:** No exploit required. Open the Network tab on `site/student/assignments.html` and read
`expected_response` for every released preflight, before the deadline. Minimum-effort version:
`GET /rest/v1/activities?select=content&slug=eq.<own slug>`. Since `preflight-analyze` grades Q3
*against* `expected_response` (`SKILL.md:375,381`), copying it yields full green credit by
construction. `assignment_offerings.content_snapshot` is a second readable copy.

**Confidence:** Confirmed for the code path and predicate. **Needs-verification** whether currently
published Fall 2026 offerings actually carry a populated `expected_response` (the builders set it
conditionally) — if empty in production, drops to Low.

**Fix:** Move `expected_response` out of the student-readable column — a `grading` object on
`assignments` or a separate `activity_keys` table with an `is_staff()` policy. Zero-DDL stopgap: strip
it from live `activities.content` for published offerings via DML — but only once the staff-side path
exists, or grading loses its grounding.

**Live-system risk:** Proper fix is DDL + data migration + changes to `preflight-analyze`,
`lesson_aggregate.py` (`:795-808,1150`) and `aggregate_summarize_test.py`. Schedule deliberately.

### SEC-04 — Written answers editable after the deadline; no deadline enforcement anywhere in the DB
**Severity:** High
**Location:** `002_rls.sql:339-343`; absence of any deadline predicate across `supabase/migrations/app/*.sql`; UI-only checks at `student-data.js:105-130` and `interaction-submit.html:181-187`

**What:** Every `app` migration was grepped for a trigger, CHECK or policy referencing `due_at`,
`due_by_day`, `extended_due_at` or any past-due notion. **There is none.** `sa_student_write` is
`FOR ALL` with no `is_final`, no `status`, no time predicate. `submitInteractionReport()` re-checks
*one* of the three UI stops server-side (already-finalized) and its own comment concedes the rest:
*"Past-due is enforced in the UI today; a DB-level deadline guard is a hardening follow-up."*
CORE.md §2 admits the *release window* is UI-only; the *deadline* being UI-only is the same defect one
step further in and is undocumented.

**Exploit:** Preflights are due 2359 and `preflight-analyze` runs *after* that. A student who submits
nothing by 2359 can write their answers at 0700 with one REST upsert and be graded normally — the
skill cannot tell. A weak submitter can replace their answers in the same window. DELETE is also
permitted, so work an instructor has seen but not finalized can be removed.

**Confidence:** Confirmed.

**Fix:** The "frozen after commit" trigger from SEC-02 covers the post-commit half. For
never-committed-and-now-late, resolve `extensions.extended_due_at → assignment_due_dates.due_at →
assignment_offerings.due_at` (the precedence `schema.js effectiveDue` implements, already ported in
`lesson_aggregate.py`) and refuse past it unless staff or `current_uid() IS NULL`.

**Live-system risk:** DDL (unseal). Mid-term risk is real: a timezone or clock-skew bug locks students
out. Ship with a grace window (e.g. `due + 1 hour`), roll out on a low-traffic day, or gate
per-offering until it has run a full lesson cycle.

### SEC-05 — Derived staff passwords plus a world-readable instructor list make staff accounts guessable
**Severity:** High
**Location:** `create-instructor/index.ts:63-68`, `reset-staff-password/index.ts:57-62`, `site/js/faculty-admin.js` (third copy); `002_rls.sql:262`

**What:** Staff initial and post-reset password is `<surname>1234`, lowercased, surname cut at the
first hyphen/space. Separately `instructors_read` is `USING (true)` — **any** authenticated user,
every cadet included, can `SELECT id, name, is_global_admin FROM instructors`, i.e. the complete staff
roster *with the system-admin flag attached*. `must_change_password` is a good mitigation but only
closes the window *after* the legitimate user signs in; a newly created account, or one reset for
someone on leave, sits on the default indefinitely.

**Exploit:** A cadet lists every instructor, picks the one with `is_global_admin = true`, and tries
`<surname>1234`. `site/login.html:29`'s placeholder is `first.last@afacademy.af.edu`, so the address
is a template. **One guess.** If that account hasn't rotated, they are faculty — which under SEC-01 is
one further call from system admin and therefore every grade and roster row in both courses.

**Confidence:** Confirmed for the derivation, the three copies and the unrestricted read.
**Needs-verification** for the production staff email format and for Supabase Auth rate limiting
(which would not blunt a single targeted guess).

**Fix:** (1) Narrow `instructors_read` to `id = current_uid() OR is_staff()` — `auth.js:62-63` only
queries it to resolve the caller's role, which still works; at minimum keep `is_global_admin` out of a
student-readable projection. (2) Generate a random staff default server-side and show it once to the
director (there is no roster to look it up on later, unlike cadets). (3) Expire the default after N days.

**Live-system risk:** (1) is a policy swap, no table DDL, seconds — but coordinate under §0 and re-run
`app_rls_test.py`, since `auth.js` role resolution depends on the read succeeding for staff. (2)
touches two edge functions and `faculty-admin.js`, which "may not drift" — deploy as one change.
Neither affects students.

### SEC-06 — Four external CDN scripts with no SRI and no CSP, over a localStorage session
**Severity:** Medium
**Location:** every page under `site/` — e.g. `interaction-submit.html:13,16-18`, `report.html:11-12`, `faculty/help.html:11-12`, `faculty/account.html:9`; `site/js/config.js:27-30`; `site/js/supabase.js`

**What:** 19 pages load `https://cdn.jsdelivr.net/npm/@supabase/supabase-js@2`; four load `marked`,
`DOMPurify` and `lz-string` from cdnjs. **No `integrity=` attribute exists anywhere in the repo**
(grepped, zero matches) and there is no CSP. The supabase-js specifier is a floating `@2`, so the
served bytes change with no commit here. The session lives in localStorage (supabase-js default;
`supabase.js` deliberately reuses one client), so any script on the origin can exfiltrate a live token pair.

**Exploit:** A compromise of either CDN executes attacker JS on every PREP page for every user,
including the course director — whose session, under SEC-01's blast radius, is the whole database. It
also means **the DOMPurify sanitizing the student-controlled `#r=` report is itself an unverified
remote script**: one CDN move neuters the sanitizer *and* the XSS defence.

**Confidence:** Confirmed.

**Fix:** Pin exact versions with `integrity=` + `crossorigin="anonymous"`. Better: vendor all four into
`site/vendor/` and serve from Pages — no build step, removes two third-party origins from the trust
boundary, squarely within CORE.md §2. Add a CSP meta once vendored (the inline theme snippet in every
`<head>` will need a hash or nonce).

**Live-system risk:** No DDL, no DB contact, normal 1–2 minute Pages rebuild. Only hazard is pinning a
supabase-js patch that differs from whatever `@2` currently resolves to — verify locally with
`python -m http.server 8000` first.

### SEC-07 — `staff_assignments.section_id` is never checked against `course_offering_id`
**Severity:** Medium
**Location:** `002_rls.sql:272-274` (`staff_write`) and `101-112` (`staff_sections()`); `001_core_model.sql:235-244` (no composite FK); `create-instructor/index.ts:198-206`

**What:** `staff_write` authorizes on `course_offering_id IN (SELECT director_offerings())` and says
nothing about `section_id`. The two FKs are independent with no constraint tying section to offering,
and `staff_sections()` reads `section_id` straight out with no join back. `create-instructor` passes
`body.section_id` through unvalidated under the service role.

**Exploit:** A Physics 110 director inserts a row naming their own offering and a **Physics 215**
section uuid. `staff_sections()` now returns that foreign section, unlocking `students_read_staff`,
`enrollments_read_staff`, `submissions_staff_read`, `sa_staff_read`, `grades_staff_read` **and
`grades_staff_write`** on students in a course they have no relationship with. The brake is needing
the foreign section uuid, which no policy discloses — but that precondition is weak: section uuids
appear in `analysis_reports` payloads, export filenames, and any URL or screenshot shared between directors.

**Confidence:** Confirmed for the policy defect; **Likely** for end-to-end exploitability.

**Fix:** `staff_write`'s `WITH CHECK` should require `section_id IS NULL OR EXISTS (SELECT 1 FROM
sections s WHERE s.id = section_id AND s.course_offering_id = staff_assignments.course_offering_id)`;
`staff_sections()` should join and confirm the same; add the equivalent to `create-instructor`.
Durable fix is a composite FK, which needs a unique index on `sections(course_offering_id, id)` first.

**Live-system risk:** Policy + function change is DDL (unseal); the `create-instructor` guard is a
function deploy with no DB impact and ships immediately as partial mitigation. Re-run
`app_rls_test.py` — `staff_sections()` is the most load-bearing helper in the schema.

### SEC-08 — Students receive the hidden AI diagnostic the docs say they never see
**Severity:** Medium
**Location:** `site/js/schema.js:40-42` (`GRADE_SELECT` includes `diagnostic`) + `student-data.js:88`; contradicts CORE.md §6 and PROJECT.md

**What:** `GRADE_SELECT` names `diagnostic`, and `loadAssignmentStatuses()` — the one loader every
student surface projects over — issues `db.from('grades').select(GRADE_SELECT)`. RLS correctly limits
this to the student's own *finalized* grades, so it is not cross-student. But the payload carries the
full `schema: 1` assessment: `overall_understanding`, `misconceptions[]` with evidence quotes,
`effort_rationale`, `reading_reflection.meaningful`, `flags.needs_follow_up`, `flags.note`, and per
`report.html:1504-1506` `honor.status` (`disclosed`/`concern`) and `honor.note`. Nothing renders it —
which is why it went unnoticed — but it is one devtools panel away, and the design docs assert twice
that it is not there.

**Exploit:** A student reads the instructor-facing AI judgment of their own work, **including whether
an honor concern was raised and its note**, before the instructor acts. Also lets them
reverse-engineer the rubric across a term.

**Confidence:** Confirmed for the wire exposure. **Needs-verification** whether `honor` is actually
populated in production.

**Fix:** Drop `diagnostic` from `GRADE_SELECT`; give faculty a separate `GRADE_SELECT_STAFF`. Check
every consumer first — it is used on both sides today, which is how the field got into the student
path. Then re-verify the CORE.md §6 / PROJECT.md claim (a doc asserting a privacy property the code
lacks is worse than silence).

**Live-system risk:** Pure frontend, no DDL, two-minute window. Grep `.diagnostic` under
`site/student/` first.

### SEC-09 — A director can re-point a student's login identity, or hard-delete a student and their grades
**Severity:** Medium
**Location:** `002_rls.sql:239-249` (`students_write`)

**What:** `FOR ALL`, with a deliberately weak `WITH CHECK (is_admin() OR EXISTS (SELECT 1 FROM
director_offerings()))` — the comment explains INSERT cannot be scoped because a student row precedes
any enrolment. But `FOR ALL` applies that weak check to **UPDATE** too, and RLS cannot restrict
columns, so `students.auth_user_id` is writable.

**Exploit:** (1) Set `auth_user_id` for a cadet they direct to a different auth user id —
`my_student_id()` resolves purely through this column, so that account *becomes* the student for every
policy: their submissions, grades, honor statements. Nulling it locks the cadet out with no trace.
(The UNIQUE constraint narrows but doesn't close this.) (2) `DELETE FROM students` cascades through
`enrollments` → `submissions`/`grades`/`extensions`/`ei_sessions`, with no soft delete, no DB-level
confirmation, and no `grade_events` entry — and `site/faculty/system.html` offers exactly this over
every table.

**Confidence:** Confirmed. Privileged-insider risk, listed because the *identity* column and the
*destructive* verb are both reachable through a policy whose comment shows the author was thinking
only about INSERT.

**Fix:** Split by verb — permissive `WITH CHECK` for `FOR INSERT` only; strict enrolment-scoped
predicate in both `USING` and `WITH CHECK` for UPDATE/DELETE. Separately
`REVOKE UPDATE (auth_user_id) ON app.students FROM authenticated` (only `provision-students` writes
it, under service role). Consider revoking DELETE entirely and routing removal through the existing
`enrollments.status = 'dropped'` path.

**Live-system risk:** The REVOKE is immediate and safe — but confirm `site/js/roster-import.js` does
not write `auth_user_id` during an import first (not traced end to end). The policy split is DDL (unseal).

### SEC-10 — Any staff member can forge audit rows in `grade_events`, for any course
**Severity:** Low
**Location:** `002_rls.sql:365-366`

**What:** `ge_staff_insert ... WITH CHECK (is_staff())` — the only predicate is "the caller is *some*
instructor somewhere". `ge_staff_read` directly above correctly scopes to `staff_sections()`; the
insert does not scope at all and does not constrain `actor`.

**Exploit:** An instructor of one section can append arbitrary events to any grade's history in either
course, attributed to any instructor, including `'finalized'` and `'reopened'`. The table's comment
calls it insurance against a retroactive rescore silently corrupting totals — an append-only log
anyone can append anything to does not provide that. `review_signoffs_require_self()` in `007` solves
exactly this problem for attestations and was not applied here.

**Confidence:** Confirmed.
**Fix:** Scope the `WITH CHECK` to the section via `grades → enrollments → staff_sections()`, and add
`AND (actor IS NULL OR actor = current_uid() OR current_uid() IS NULL)`.
**Live-system risk:** Policy replacement (DDL, unseal). Zero student impact; the analysis scripts write
through the DML tier and bypass RLS, so they are unaffected.

### SEC-11 — The whole assignment library, both courses, is readable by any staff member
**Severity:** Low
**Location:** `002_rls.sql:182-183` and `192-193`

**What:** Both `USING (is_staff())` — no course, offering or term predicate. Any instructor reads every
assignment and activity in the schema, including `activities.content` (and thus, per SEC-03, the model
answers) for courses they do not teach.

**Exploit:** Cross-course visibility of unreleased content and answer keys among staff. Plausibly
intentional in a two-course department, but it is not what the surrounding policies do — everything
else scopes to `director_courses()` / `staff_offerings()` — and nothing documents the exception. It
means one compromised instructor account exposes the other course's entire question bank.

**Confidence:** Confirmed.
**Fix:** If cross-course sharing is wanted, record it as an explicit decision in
`docs/decisions/PREP-V2-AUTHORIZATION.md`, which currently describes a uniform two-predicate model
these two policies silently break. Otherwise scope to `director_courses()` plus the offerings the
caller staffs.
**Live-system risk:** Policy replacement (DDL, unseal). Risk of over-tightening and blanking a
director's lesson list mid-term — test against the `app_rls_test.py` instructor fixture first.

### SEC-12 — Open redirect on the login page via a backslash
**Severity:** Low
**Location:** `site/login.html:58-63`

**What:** `if (n && n.startsWith('/') && !n.startsWith('//')) return n;` — the guard blocks
protocol-relative `//host`, but the WHATWG URL parser treats `\` as `/` for special schemes in the
relative-slash state. `?next=/\evil.example` starts with `/`, does not start with `//`, and resolves
to `https://evil.example/` under `location.replace()`.

**Exploit:** A phishing link on the real PREP origin that redirects a cadet or instructor to an
attacker-controlled sign-in clone the moment they authenticate — or immediately, since the
already-signed-in branch (`login.html:76-79`) calls `safeNext()` too. Credential value is high given
SEC-01 and SEC-05.

**Confidence:** Likely — the URL-spec behaviour is unambiguous, but not executed in a browser.
**Fix:** `if (n && /^\/[^/\\]/.test(n)) return n;`, or resolve and re-check the origin with
`new URL(n, location.origin)`.
**Live-system risk:** One line, frontend only, two-minute window. The `?next=` values `auth.js:55`
generates (`pathname + search`, always `/Core_Preflights/…`) still pass.

### SEC-13 — Edge functions: wildcard CORS and 200-with-error-body
**Severity:** Low
**Location:** all six of `supabase/functions/*/index.ts` — e.g. `create-instructor/index.ts:37-47`, `reset-student-password/index.ts:36-49`

**What:** All set `Access-Control-Allow-Origin: "*"` and return HTTP 200 for every outcome,
authorization refusals included.

**Impact:** CORS is **not** CSRF-exploitable here — the session is a bearer token in localStorage, not
a cookie, so a cross-origin page cannot read it and the browser will not attach it. Residual risk is
only that a stolen token works from anywhere and a free defence layer is discarded. The 200-on-failure
convention is deliberate and documented (a non-2xx makes supabase-js throw `FunctionsHttpError` and
swallow the operator's message), but it means the function logs and any uptime monitor see 100%
success — including a sustained run of `"Only course directors or system admins can add instructors"`,
which is what an authorization probe looks like. **There is no signal anyone is attacking these endpoints.**

**Confidence:** Confirmed.
**Fix:** Set the origin to `https://dfpm-physics.github.io` (plus `http://localhost:8000` for local
verification). Keep the 200 convention but add a distinguishable field (`{ error, code: "forbidden" }`)
and `console.warn` refusals so they surface in the logs.
**Live-system risk:** Function redeploys only. Check `tests/browser-harness/` before tightening CORS.

### SEC-14 — No size ceiling before decompressing the attacker-controlled hash payload
**Severity:** Low
**Location:** `site/student/interaction-submit.html:11` (pre-module stash) and `49-52` (`unpack`)

**What:** `location.hash` is stashed into sessionStorage unconditionally, then passed to
`LZString.decompressFromEncodedURIComponent()` with no length check on either side. The DB caps are
correct (`report_markdown` ≤ 100 KB, `content` ≤ 32 KB, `001_core_model.sql:376-379`) but apply at
INSERT, long after the browser has decompressed and Markdown-rendered.

**Exploit:** A crafted URL with a high-ratio LZ payload expands to hundreds of MB before
`marked.parse`/`DOMPurify.sanitize` run, hanging the tab. The URL is shareable, so this is
student-to-student griefing — a classmate is handed what looks like a lesson report and their browser
dies. The stash happens *before* any authorization, so an unauthenticated visitor can be hit.

**Confidence:** Confirmed for the missing check; **Needs-verification** for the practical expansion
ratio within a URL-length limit.
**Fix:** Refuse a raw hash over ~150 KB before stashing; after decompression refuse `markdown` > 100 KB
/ `data` > 32 KB — the same numbers the CHECK constraints use, so the page rejects what the DB would
reject and explains why.
**Live-system risk:** Frontend only, two-minute window. Set the ceiling above the largest real report
to date (`submission_activities.payload_bytes` records it).

### SEC-15 — The academic-calendar publish token is committed and served publicly
**Severity:** Low
**Location:** `site/data/academic-calendar.json:4` and `scripts/calendar/build_academic_calendar.py:60`

**What:** Both carry the Outlook publish URL embedding a GUID-form mailbox identifier
(`d8fbe643…@afacademy.af.edu`). GitHub Pages serves the repository root, so the script itself is
fetchable at a public URL, as is the JSON.

**Impact:** Anyone who finds it can read the calendar feed indefinitely; the token is a bearer
capability with no revocation short of re-publishing. The data is a published academic calendar, hence
Low — but it is a credential-shaped string in a public repo and should be a deliberate decision.

**Confidence:** Confirmed for the exposure; the sensitivity judgment is the auditor's.
**Fix:** If the feed is genuinely public, say so in the script header so the next reader doesn't treat
it as a leak. Otherwise move the URL into the gitignored config alongside the other secrets.
**Live-system risk:** None. The JSON *output* must stay committed (CORE.md §2: CORS blocks a browser
fetch, no build step); only the URL in the header and the `source` field move.

## Positive findings

**RLS genuinely backstops the client gates — verified, not assumed.** The most important result of the
audit; it inverts the July 2026 `public` findings.
- `site/faculty/system.html` offers generic INSERT/UPDATE/DELETE over **every table in `app`**, gated
  in the browser only by `!!ctx.instructorRow.is_global_admin`. Every write goes through the ordinary
  anon-key client, so RLS applies unchanged — `site/js/system-admin.js:81` has an `rlsHint()` helper
  precisely because refusals are expected. The comment at `system.html:82` states the boundary
  correctly: *"the is_global_admin check below is a UX boundary."* It is.
- Lesson authoring (`isDirector()`) is backed by `assignments_write`, `activities_write`, `ao_write`,
  `oa_write`, `due_write`, all on `director_offerings()` / `director_courses()`.
- Grading scope (`actionableSections()`) is backed by `grades_staff_write` and `staff_sections()`.
- Admin feedback is backed by `feedback_admin_read USING (is_admin())`, with no UPDATE/DELETE policy
  until `013` adds an admin-only one.
- `ei_sessions` has **no student policy**, deliberately, and `011`'s header explains why — the absence
  *is* the enforcement, and it holds.

**Anon really does get nothing.** Not one policy in the entire `app` chain grants `anon` anything. The
bootstrap's table-wide GRANT to `anon` is inert because every policy is `TO authenticated`. This closes
all four original `public` audit findings by construction.

**Students cannot reach each other's data.** Every per-student table traced — `submissions`,
`submission_activities`, `grades`, `extensions`, `enrollments`, `students`, `user_preferences`,
`analysis_reports`, `ei_sessions`, `feedback`, `roster_imports`, `analysis_runs`, `review_signoffs`.
Each resolves to `my_enrollments()` / `my_student_id()` / `current_uid()` or has no student policy.
`grades_own_finalized` correctly carries **both** the owner predicate and `is_finalized`, so a draft AI
grade is invisible until published. `analysis_reports` is closed to students on all three scope branches.

**XSS discipline is excellent and consistent.** Every Markdown path is
`DOMPurify.sanitize(marked.parse(...))`, in that order, without exception — including repo-authored
help content, which `help.js:220-222` sanitizes anyway on principle. Every template-literal
interpolation of DB-sourced text sampled across `grade.html`, `student.html`, `report.html`,
`assignments.html`, `interaction-submit.html`, `faculty-rollup.js` and `system.html` goes through
`esc()`. `report.html:1519` even escapes *unrecognized* flag keys with a comment explaining why.
**No unescaped sink was found.**

**`javascript:` URLs are structurally blocked.** `schema.js:369-376` `isArtifactLaunchable()` tests
`/^https?:\/\//i` and is the single gate for both the `href` in `lessons.html:478-483` and the
`window.open` in `student/lessons.html:194-198`, with the reason stated in both.

**The forced-rotation flag is in the right bag.** `must_change_password` lives in `app_metadata`
(service-role-only), not `user_metadata` — `reset-student-password/index.ts:30-34` names the exact
attack that motivated the move. `auth.js:125-138` handles the stale-JWT-copy problem correctly: a set
flag triggers one `getUser()` round trip rather than trusting the cached snapshot, and a dead session
signs out rather than looping. The redirect **cannot** be bypassed client-side.

**The password functions refuse rather than ignore.** `reset-student-password:70-75` and
`reset-staff-password:78-83` both error when a `password` parameter arrives instead of silently
dropping it — so a UI that appears to set passwords cannot ship by accident.

**`set-own-password` is well built.** Re-verifies the current password server-side (which
`updateUser` does not), using a throwaway client so the caller's session isn't clobbered, and skips
that check only under forced rotation, with the reasoning written down.

**Edge-function authorization is done properly.** All six verify the JWT via an anon-key `getUser()`
(server-validated), then re-check authorization with the *service* client against
`instructors`/`staff_assignments`. Crucially, all require the **target** to be reachable through the
named offering — `reset-student-password:125-148` joins `sections → enrollments`,
`reset-staff-password:150-161` joins `staff_assignments` — with the cross-course attack that omission
would allow spelled out in each. `create-instructor`/`remove-instructor` correctly refuse to let a
director act on a system admin, and `create-instructor` dropped the legacy `is_director`
second-admin-flag bug rather than porting it. `create-instructor` rolls back cleanly on partial
failure. Passwords are never returned in a response body, with the proxy-log reasoning stated.

**Migration 006 is a model of the right fix in the right layer.** Closed two real student-found
bypasses (self-unlock by misattribution; status-revert-then-switch) in the *trigger* rather than in
RLS, with an explicit argument for why — `WITH CHECK` cannot see `OLD`, so it cannot recognise a
transition. `007` applies the same reasoning to extension withdrawal. **That instinct is correct and
should be reused for SEC-02 and SEC-04.**

**Secrets hygiene is clean.** `.gitignore` covers `*.env` / `.env*`, `config.json`,
`supabase/admin/config.json`, `supabase/admin/config.*.json`, `.venv/`, `textbook-pdfs/**/*.pdf`,
`_snapshots/`. `git ls-files` confirms `supabase/admin/.env` and `supabase/admin/config.json` exist on
disk and are **untracked**. `git log --all --diff-filter=A` over the whole history shows only
`*.template` files were ever added under those names — **no credential file was ever committed and
later removed**. No JWT-shaped string in any tracked file. The anon key in `site/js/config.js` is the
publishable key and is correctly documented as safe to commit.

**No real student PII is tracked.** Every file containing a cadet-ID-shaped number was checked.
`scripts/fall2026/poc-archive/*.json` (206 students, 558 responses, 600 scores) and
`scripts/test-data/phys215-test-roster.csv` are **synthetic** — IDs in the `30001000xx` band with
fabricated names (Jordan Blake, Riley Nguyen, Alex Carter). `supabase/seed_full.sql` likewise.
`CHANGELOG.md` contains no keys and no real cadet identifiers. This matters more than usual: GitHub
Pages serves the repository root, so anything tracked here is world-fetchable.

**The login form is not a roster oracle.** `login.html:104-108` returns one identical message for every
auth failure, with a comment noting it is deliberately not reproducing the legacy bug.

**Size caps exist where they matter at rest.** `submission_activities` caps `report_markdown` at 100 KB
and `content` at 32 KB; `user_preferences` at 16 KB; `ei_sessions.notes` at 4 KB; `feedback.message` at
4 KB. `010`'s header states outright that nothing in `user_preferences` may ever affect authorization.

## What could not be verified statically

1. **Whether the live database matches the committed migrations.** Biggest caveat; applies to SEC-01,
   04, 07, 09, 10, 11. `docs/decisions/PREP-V2-AUTHORIZATION.md:3` says the policies were "written…
   not yet applied," and CORE.md §5 warns adding a migration ≠ applying it. **Before acting on SEC-01**,
   confirm read-only as `postgres`:
   `SELECT polname, polcmd, pg_get_expr(polqual, polrelid), pg_get_expr(polwithcheck, polrelid) FROM pg_policy WHERE polrelid = 'app.instructors'::regclass;`
   and `SELECT * FROM information_schema.column_privileges WHERE table_schema='app' AND table_name='instructors';`
2. **Whether migration 015 is applied** — SEC-02's severity depends on the autograde trigger being live.
3. **Whether `expected_response` is populated** for currently published Fall 2026 offerings (SEC-03 High if yes, Low if no).
4. **The staff sign-in email format** (SEC-05).
5. **Supabase Auth rate limiting** on `signInWithPassword`, which bounds how broadly SEC-05 can be swept.
6. **Whether the repository is public.** Pages-from-`main` implies it; materially affects SEC-15 and the PII conclusion.
7. **Actual browser behaviour of `location.replace('/\\host')`** (SEC-12).
8. **The deployed edge-function versions** vs. the repo source.
9. **The LZString expansion ratio** achievable within a practical URL length (SEC-14).
10. **`site/js/roster-import.js` end to end** — matters for the SEC-09 remediation.
11. **`[DEFERRED-ARTIFACTS]`** — two things deserve a follow-up pass: migration `023` introduces
    **Supabase Storage**, which has its own bucket policies entirely outside the RLS model audited
    here; and `_builder/courses/*/artifacts/*.jsx` is gitignored while `BUILD-LOG.md` /
    `REVIEW-NOTES.json` beside it are tracked — worth confirming those carry no student text.
