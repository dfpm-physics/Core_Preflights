Gemini implicit-cache probe

Does a free-tier Gemini key get implicit context caching — and does the tutor prompt's own layout throw the discount away? Seven real requests. Nothing is stored.

Minimum cacheable prefix is 1,024 tokens on Flash and 4,096 on Pro. Below it, nothing caches and no error is raised. 8,000 is comfortably clear of both and is about half a real median lesson prompt (~17,400 tokens).

THE CACHED COUNT IS THE VENDOR GRADING ITS OWN HOMEWORK. cachedContentTokenCount is Google reporting on Google's billing. It is reproducible and it passes the negative control, which is why it is trusted here — but no saving derived from it has been checked against a bill, because a free key produces no bill. The Time column is the one number here Google does not self-report: a real hit skips prefill, so at 36,900 tokens it should be visibly faster than the write before it. A "hit" that takes as long as its write is a reason to doubt the field.

RECORD THE MODEL BESIDE EVERY NUMBER. modelVersion is on every reply and it was being thrown away. gemini-3.5-flash hit on the second call every time (2026-09-17, 7,733–36,292 tokens). gemini-3.6-flash returned no cache field on 8 consecutive same-prefix calls (2026-09-18, 7,734–8,007 tokens).

That comparison is CONFOUNDED — different models on different days, because 3.5 had run out of free quota. The 18th also threw repeated 503s, so a platform-wide degradation fits the data as well as the model does. To settle it, run experiment 6 on one model and then immediately on the other, same day. Anything else reproduces the confound.

Free-tier rate limit is 5 requests per MINUTE on gemini-3.6-flash, measured from the 429 body on 2026-09-18 — not 15. The gap now defaults to 15 seconds. Lower it and any run of four or more calls will trip the limit partway through.

Experiments

1–3
Does free tier cache at all? Cold write, then the same prefix again with a different question, then a deliberately different prefix as a control. Three requests. This is the one that answers the question — run it first.
4
Name at the front — the shipped layout Two calls. A unique cadet id sits ~850 characters in, exactly where buildSystemPrompt puts it today. Expect no hit on call 2.
5
Name at the end — the proposed fix Two calls. Same prefix, same unique ids, but placed after all the stable text. Expect a hit on call 2.
6
Does the hit grow with the prompt? A cold write and a warm read at three sizes — 8,000, 17,400 and 36,900 tokens, the smallest, median and largest real lesson prompts. Six requests. The 7,730-token run cached 4,076 (53%). If that number is the same at 36,900 the saving is small; if it tracks the size, the saving is large. This is the difference between a modest win and a big one.
8
Did within-session caching ever work? A real session, simulated: one cadet name, one model, and a conversation that grows turn by turn — the shipped layout, name at the front, which is fine within a session because it never changes. Five requests. Every earlier experiment used a single turn and so never asked this. Expect a hit from turn 2 onward. If that is what happens, a stable prefix was already worth ~60% and the name was never the problem it looked like.
9
Does switching model throw the cache away? Warm a prefix on the chosen model, switch to the walk-to model, then come back. Four requests. PREP walked a rung on every 429 or 5xx against a 20/day cap — so if a walk is a cold start, that alone explains paying full price with a perfectly good prefix. Expect the walk-to call to miss; the question is whether the original model still hits when you return.
7
No name anywhere Two calls with a byte-identical prompt — no cadet id at the front, the end, or at all. Only the trailing question differs. This is the best case caching can have. Compare its cached count against row 5b: if 7 beats 5, the name costs something even at the end and should be kept out of the prompt entirely.
