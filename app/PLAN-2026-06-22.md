# Portal refactor — work plan (2026-06-22)

Author: Matthew Recker. Scope: the `app/` portal only (no changes to legacy root pages
unless noted). Direction for the day: **shift the faculty experience toward lesson
interactions as the primary signal**, deepen the interactions reporting, and start a
**native admin page**.

This plan turns five requests into scoped, dependency-ordered work items. Each item lists
what exists today, what to build, the files it touches, and any blockers.

---

## Current state (verified 2026-06-22)

- **Dashboard** (`faculty/dashboard.html`): stat tiles (sections / students / submissions to
  grade / avg submitted) → quick actions → **Section roll-up**. The roll-up
  (`js/faculty-data.js → loadFacultyDashboard`) shows directors *all* sections in one grid
  and instructors only their own; each card mixes per-assignment preflight rows + one
  interactions completion row.
- **Interactions** (`faculty/interactions.html` + `js/faculty-interactions.js`): per-interaction
  cards with completion % and per-section chips. "View reports" opens a modal with
  section/student dropdowns. The data layer computes **counts** of reports, not the **set of
  students** who completed — and there is no completion list tied to the progress bar.
- **Course-level interaction rollup**: does not exist.
- **Admin**: no native page. Nav's "Admin ↗" (`js/nav.js:23`) opens legacy `admin.html` in a
  new tab. Visible to all faculty, not director-gated.
- **Edge functions**: `create-instructor`, `remove-instructor`, `provision-students`. **No
  password-reset function exists.**
- **Roles** (`js/auth.js`): `is_global_admin`, `is_director`, `instructor_course_access.role`,
  surfaced via `ctx.isDirectorForCurrent()`. Section scoping is client-side (RLS permissive).

## Work items

### A. Section roll-up: my sections vs. all-other sections (request #2)
- **Now:** directors see every section in one undivided grid.
- **Build:** split the roll-up into **"Your sections"** (where `instructor_id` = me) and, for
  directors/admins only, a second **"All other sections"** group. Instructors see only the
  first group (unchanged for them). Keep one query; partition in JS by `instructor_id`.
- **Files:** `js/faculty-data.js` (return `mySections` + `otherSections`), `faculty/dashboard.html`
  (`rollup()` renders two labeled groups; second is director-gated).
- **Blockers:** none. Small.

### B. Section roll-up: interactions only (request #3)
- **Now:** roll-up cards render per-assignment preflight rows plus an interactions row.
- **Build:** drop the per-assignment rows from the roll-up card; keep only interaction
  completion (ideally per-published-interaction, not one merged bar). **Decided (2026-06-22):
  also retire the assignment-centric stat tiles** ("submissions to grade", "avg submitted") in
  favor of interaction metrics (e.g. avg interaction completion, lessons published, students),
  to keep the dashboard internally consistent with the interactions-first test. Preflight
  grading still lives on the Grade/Report tabs — this only changes the dashboard summary.
- **Files:** `js/faculty-data.js` (stop computing/returning `perAssignment`; expand interaction
  detail), `faculty/dashboard.html` (`rollup()`, `statTiles()`).
- **Blockers:** none. Do A + B together — same two files.

### C. Interaction progress bar → completion list + per-student report (request #4)
- **Now:** report viewer is dropdown-driven and count-only; clicking the bar does nothing.
- **Build:** make the per-interaction (and per-section) progress bar clickable → opens a panel
  showing the **aggregate report** for that lesson plus a **roster list**: every student with a
  ✓/○ completion state, and a **view-report icon next to each completed student** that opens
  their saved report. Requires the data layer to return the **set of completing students per
  interaction** (not just counts). "Aggregate report" = the course/section-wide summary for
  the lesson; until the aggregation pipeline exists (see E), show completion stats + a
  "summary pending analysis" placeholder.
- **Files:** `js/faculty-interactions.js` (+ maybe `faculty-data.js`) — add per-interaction
  `completedStudentIds`; `faculty/interactions.html` — clickable bars, completion list,
  per-student report icon (reuse `loadReport` + DOMPurify render).
- **Blockers:** "aggregate report" body depends on D's aggregation; completion list + per-student
  report viewing do **not** — build those now.

### D. Course-level interaction rollup in Quick Actions (request #1)
- **Now:** nothing.
- **Build:** a course-wide interactions overview reachable from Quick Actions: most-missed
  lesson, lowest-understanding concepts, completion rates, then click a lesson → course-wide
  stats for it (drills into C's per-lesson view).
- **Files:** new `faculty/interactions-overview.html` + `js/faculty-interactions-overview.js`;
  quick-action link in `faculty/dashboard.html`.
- **Blockers (important):** "most misunderstood lesson / lowest-understanding concept" needs an
  **aggregation step that does not exist yet** — the analysis-skill output for interactions, and
  the CLAUDE.md "Deferred" decision on *where that output is stored* (new table vs.
  `analysis_report`-style JSONB). **Status (2026-06-22): TBD — a separate AI effort is building
  the aggregation; we'll match its output shape once it lands.** **Completion rates are computable
  from existing `preflight_interaction_reports` today.** Plan: ship the overview shell +
  completion-rate rollup now; stub concept/misconception cards behind a "pending aggregation"
  state and wire them once the pipeline + storage land.

### E. Native admin page (request #5)
- **Now:** legacy `admin.html` only; no password reset anywhere; section moves exist in the
  director Roster/Sections page (`assignInstructor`, `updateStudentSection`).
- **Password model (decided 2026-06-22):** two complementary mechanisms.
  1. **Self-service email reset link** — the primary path. Any user can request it; an admin
     (instructor for own students, director for all) can also trigger it for someone. Uses
     Supabase Auth password-recovery email. *Caveat:* students are provisioned as
     `studentId@usafa.edu` — those inboxes must actually receive mail for student self-service to
     work; if not, students fall back to the temp-password path via their instructor. (Verify
     deliverability before relying on it for students.)
  2. **Assign a temporary password** — an explicit option, primarily for **instructors/directors**
     (and available as the student fallback). Sets a known temp password server-side and shows it
     once to the admin to hand off.
- **Build:** `faculty/admin.html`, faculty-only, with director-elevated sections:
  - **Instructor:** trigger a reset **email**, or assign a **temp password**, for **their own**
    students.
  - **Director/admin:** the same for **all** students **and** instructors in the course; move
    section assignments (instructor↔section, student↔section — reuse existing roster fns).
  - Add a **"Forgot password?"** self-service link on `login.html` (client-side
    `resetPasswordForEmail`, no privilege needed) + a recovery-handler page for the email redirect.
  - Point nav's "Admin" link at this page (drop the external/legacy target).
- **New backend (long pole):** a **`reset-password` edge function** with two modes —
  `mode:'email_link'` (send recovery email) and `mode:'temp_password'` (set + return a temp
  password). Client SDK cannot set another user's password, and admin-initiated email triggers
  need authorization, so both run server-side with the service-role key and verify: instructor →
  target must be a student in a section the caller teaches; director → any student/instructor in
  the caller's course; SA → anyone. `temp_password` for an instructor/director target is
  director/SA-only. Mirror the existing functions' JWT-verify + `{ success }` / `{ error }`
  contract and rollback discipline. (Pure self-service from `login.html` needs **no** function —
  it's a direct anon-key `resetPasswordForEmail` call.)
- **Files:** new `supabase/functions/reset-password/index.ts`; new `faculty/admin.html` +
  `js/faculty-admin.js`; `login.html` + a recovery page; `js/nav.js` (retarget Admin link); reuse
  `js/faculty-roster.js` for moves.
- **Blockers:** the edge function is security-sensitive and gates the admin-initiated paths — build
  and test it first. Temp-password default for students: last-6-of-ID (matches provisioning).

## Recommended priority order

1. **A + B — Roll-up: interactions-only, split my/other sections.** Fast, foundational, sets the
   interactions-first direction. One PR, two files. *(Smallest, unblocks the visual direction.)*
2. **C — Completion list + per-student report viewer.** Self-contained, high value, no new
   backend; its per-student data layer is reused by D. *(Build the completion list now; leave the
   "aggregate summary" body as a placeholder.)*
3. **D — Course-level interaction overview (completion portion).** Ship the shell + completion-rate
   rollup; stub concept/misconception analytics behind "pending aggregation." *(Partially blocked
   on the aggregation pipeline — do the unblocked half.)*
4. **E — Native admin page.** Largest and security-sensitive. Sequence within: (1) `reset-password`
   edge function + authz tests, (2) admin page shell + nav retarget, (3) instructor self-scope
   reset, (4) director elevation (all students/instructors + section moves). *(Long pole = the
   edge function.)*

Rationale: 1→2→3 are an increasing-effort chain on the same interactions data, each unblocking the
next; 4 is independent and heaviest, so it runs last (or in parallel by whoever owns the backend).

## Decisions (2026-06-22)
- **B:** ✅ retire the assignment-centric stat tiles too — go interactions-only on the dashboard.
- **D:** ⏳ aggregation pipeline still owned by a separate AI effort; the completion half is built.
  **Data contract decided:** the aggregator receives data exported *from this site* as plain
  `report_markdown` (no structured `report_data`/view route for now). Name + student ID + score is
  **not treated as PII**, so reports go out as-is — protected by faculty auth + RLS, not by content
  redaction (an earlier `redactReport()` step was removed once that was settled).
  `buildLessonCorpus()` concatenates a lesson's reports into one document, one block per student
  labeled name · ID · section (Export-for-analysis button in the report modal).
- **E:** ✅ both — a self-service **email reset link** (users can request their own; admins can
  trigger it) **and** an option to assign a **temporary password** (chiefly for instructors/
  directors, also a student fallback). Verify `@usafa.edu` mail deliverability before relying on
  email self-service for students.
